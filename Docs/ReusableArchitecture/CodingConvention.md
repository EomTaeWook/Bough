# 공통 C#·Markdown 작업 규칙

> 카탈로그: [재사용 아키텍처](README.md)
> 상태: 프로젝트 독립 적용 지침
> 문서 종류: 공통 컨벤션
> 적용 대상: C#·Unity·Markdown 저장소

이 문서는 여러 프로젝트에서 반복해서 사용하는 작업 방식과 표현 규칙만 정의한다. 실제 타입, 경로, 프레임 반복 방식, 데이터 생성 명령과 빌드 명령은 호스트 프로젝트의 적용 문서에서 확정한다.

## 1. 적용 순서

1. 현재 경로에 적용되는 `AGENTS.md`와 하위 지침을 먼저 읽는다.
2. 호스트 프로젝트의 코딩 컨벤션과 구조 문서를 읽는다.
3. 이 문서에서 필요한 공통 규칙을 적용한다.
4. 특정 상태·동기화·서버 구조가 필요하면 해당 재사용 아키텍처 패키지를 추가로 읽는다.

규칙이 충돌하면 호스트 프로젝트 지침을 우선한다. 충돌을 임의로 절충하지 않고 프로젝트 적용 문서에 선택한 차이를 기록한다.

## 2. 작업 범위와 소유권

- 요청 해결에 필요한 최소 파일만 변경한다.
- 기존 작업 트리의 변경은 다른 작업자의 소유로 취급한다. 요청과 무관한 변경을 정리하거나 복원하지 않는다.
- 사용자의 최신 지시와 총괄이 확정한 최종 계약을 적용한다. 지연 도착한 이전 작업 지시가 폐기된 계약을 복원하지 않게 한다. 인계에는 변경 경로·최종 계약·남은 의존성과 검증 미실시를 적는다.
- 구현 전에 값과 규칙의 원본 문서를 찾는다. 같은 계약을 코드, 데이터와 여러 문서에 복사해 각각 관리하지 않는다.
- 미래 확장을 위한 빈 추상화, 사용하지 않는 필드, 임시 호환 계층과 범용 `Helper`를 미리 추가하지 않는다.
- 현재 계약에 없는 폴백 값이나 매직 넘버로 오류를 숨기지 않는다.
- 생성 파일과 외부 도구 산출물은 원본을 찾은 뒤 생성 절차를 통해 변경한다.

### 영속 저장소와 데이터 소유권

- 초기화 순서, Scene, 프로세스와 실행 진입점이 다르다는 이유로 같은 책임이나 같은 개념 데이터를 소유하는 Storage, Repository, Cache, 저장 DTO, 파일과 스키마를 복제하지 않는다.
- 개념마다 하나의 authoritative persistence owner를 정한다. 다른 계층과 실행 경로는 그 소유자를 주입받거나 경계 DTO로 변환해 사용하며, Cache는 원본을 대체하는 별도 권위자가 되지 않는다.
- 새 Storage, Repository 또는 Cache를 만들기 전에 같은 데이터를 생성·로드·저장·변경·소비하는 기존 구현, 저장 모델, bootstrap, 의존성 등록과 호출 경로를 검색한다. 검색 범위와 기존 경계의 재사용 가능성은 변경 설명이나 관련 설계 문서에 기록한다.
- 기존 저장소에 접근하기 어렵다면 저장소를 복제하지 않고 bootstrap, 의존성 주입, 공통 interface 또는 provider 경계를 고친다. 실행 경로별 편의를 위해 같은 데이터의 두 번째 파일이나 DTO를 만들지 않는다.
- 인증 정보와 사용자 환경설정처럼 수명, 보안 수준, 삭제·복구 정책이 다른 데이터는 편의를 위해 하나의 저장 DTO에 섞지 않는다. 필요한 저장 보호와 수명 경계를 각각 표현하되 같은 개념의 권위 저장소를 다시 만들지는 않는다.
- 새 저장소가 반드시 필요하면 구현 전에 책임, 수명, 보안 경계, 파일 또는 스키마, 기존 저장소와 중복되지 않는 근거, 호출·의존성 경계, 마이그레이션과 롤백 계획을 코드 리뷰 가능한 문서에 남긴다.
- 저장소를 통합하거나 교체할 때는 기존 사용자 데이터를 한 번만 이전하는 마이그레이션과 실패 시 복구 경계를 먼저 마련한다. 기존 데이터 최초 실행, 마이그레이션 후 재실행과 필요한 재인증 흐름을 검증해 중복 이전, 데이터 유실과 반복 인증이 없는지 확인한다.
- 저장소 변경을 완료할 때는 모든 읽기·쓰기 호출자가 하나의 권위 경계를 사용하고 구 저장 경로가 더 이상 데이터를 갱신하지 않는지 검색과 테스트로 확인한다.

## 3. C# 표현 규칙

### 형식

- 직접 관리하는 C# 프로젝트는 nullable 정책을 프로젝트 전체에서 하나로 유지한다. nullable 비활성화 프로젝트는 `<Nullable>disable</Nullable>`을 사용한다.
- nullable 비활성화 프로젝트에서 `?`, null-forgiving 연산자와 `#nullable enable`로 파일 단위 예외를 만들지 않는다.
- 선택적 도메인 상태는 nullable 대신 `None` 또는 `Unknown`을 포함하는 enum이나 책임이 명확한 상태 객체로 표현한다.
- `sealed`를 사용하지 않는다.
- 파일 범위 네임스페이스 대신 `namespace { }` 블록을 사용한다.
- 기본 생성자 문법이나 주 생성자 문법을 사용하지 않고 명시적인 생성자를 작성한다.
- 식 본문 멤버와 한 줄 블록을 사용하지 않는다. 속성, 메서드와 제어문은 여러 줄 블록으로 작성한다.
- `if`, `else`, `for`, `foreach`, `while` 등의 중괄호를 생략하지 않는다.
- Boolean과 null 조건은 `== true`, `== false`, `== null`, `!= null`처럼 비교 의도를 명시한다.
- 삼항 연산자, `checked`, `unchecked`와 익명 객체는 사용하지 않는다.
- 메서드 호출의 첫 번째 인자는 여는 괄호와 같은 줄에 둔다. 인자가 길면 이후 인자를 줄 단위로 정렬한다.
- 저장소가 정한 줄 끝, 문자 인코딩과 파일명 규칙을 유지한다.

### 조건과 반환값

- 서로 다른 실패 원인을 하나의 복합 조건에 섞지 않는다. 검증 조건을 분리하고 각 오류를 구체적으로 표현한다.
- 호출 결과를 사용하지 않으면 의미 없는 지역 변수에 저장하지 않는다.
- 계약상 결과가 필요하지 않은 메서드는 상태 코드나 임시 Boolean을 반환하지 않고 `void`로 작성한다.
- 정상 입력에서 발생할 수 있는 실패는 경계에서 검증하고, 불가능해야 하는 내부 상태는 조용히 보정하지 않는다.
- 예외 메시지에는 실패한 대상과 이유를 포함하되 비밀값과 개인 정보는 넣지 않는다.

### 의존성과 정적 접근

- 서비스, 저장소, 핸들러와 시간·난수 공급자는 생성자 주입을 기본으로 한다.
- 전역 정적 서비스와 정적 저장소를 런타임 상태의 소유자로 사용하지 않는다.
- 정적 사용은 진입점, 부작용 없는 확장 메서드, 상수처럼 상태를 소유하지 않는 범위로 제한한다.
- 도메인 로직은 가능한 한 자신의 소유 타입 가까이에 둔다. 여러 모듈의 내부 상태를 동시에 아는 중간 관리자를 만들지 않는다.

## 4. 구조 규칙을 선택하는 방법

이 문서는 특정 상태 머신이나 네트워크 구조를 자동으로 채택시키지 않는다. 해결할 문제가 다음 적용 대상과 일치할 때만 해당 문서를 함께 사용한다.

| 문제 | 추가로 읽을 문서 |
|---|---|
| 메일박스 Actor의 입력 허용 상태와 비동기 전환 | [`ActorState`](ActorState.md) |
| 결정론적 도메인 상태와 저장·복원 | [`DomainStateMachine`](DomainStateMachine.md) |
| 클라이언트 예측, 서버 재현과 권위 정산 | [`ReplayValidationSync`](ReplayValidationSync.md) |
| RepoDB와 snake_case 컬럼 연결 | [`RepoDbSnakeCaseMapping`](RepoDbSnakeCaseMapping.md) |

- 프로젝트가 채택하지 않은 Request·Event·Queue·State 구조를 컨벤션만 보고 추가하지 않는다.
- 요청은 행위의 입력, 이벤트는 확정된 사실의 출력이라는 경계가 필요하면 호스트 문서에 먼저 채택 여부와 소유자를 기록한다.
- UI와 네트워크 표현은 도메인 상태를 직접 소유하지 않고, 채택된 계약을 통해 읽고 전달한다.

## 5. 시간, Tick과 난수

- 시간 필드와 변수 이름에 단위를 드러낸다. 예: `DurationMs`, `ElapsedSeconds`, `UpdatedAtUtc`.
- 도메인 Tick과 `DateTime.Ticks`를 같은 의미로 사용하지 않는다.
- 저장 단위, 전송 단위와 런타임 단위가 다르면 변환 경계를 한 곳에 둔다.
- 재현 가능한 결과가 필요한 로직은 프로젝트가 지정한 Seed와 난수 공급자를 사용한다.
- 결정론 계약 안에서 `System.Random`, 현재 시각, 프레임 시각과 순서가 불안정한 컬렉션을 직접 사용하지 않는다.
- Unity 프레임 반복은 호스트 프로젝트가 선택한 `Update`, Coroutine 또는 별도 Scheduler 정책을 따른다. 같은 책임에 두 번째 반복 체계를 섞지 않는다.

## 6. 게임 데이터와 생성물

- 원본 스프레드시트나 스키마를 수정한 뒤 JSON, C# 템플릿과 클라이언트 미러를 정해진 순서로 생성한다.
- 생성된 JSON과 C# 파일을 직접 수정하지 않는다.
- 데이터 수정 요청에 변환과 검증이 포함되어 있다면 원본 편집에서 멈추지 않고 생성 파이프라인과 참조 검증까지 완료한다.
- 새 필드와 테이블을 추가할 때는 이름, 타입, 필수 여부, 참조 대상, 중복 키와 빈 행을 확인한다.
- 여러 출력 경로가 같은 데이터를 가져야 하면 구문, 행 수와 해시 또는 내용 일치를 검사한다.
- 생성 데이터 접근 방식은 호스트 프로젝트의 로더 계약을 따른다. 별도 Catalog나 캐시 계층을 관성적으로 추가하지 않는다.
- 스프레드시트 전용 런타임이 없고 OOXML을 직접 수정해야 한다면 필요한 셀과 관계만 최소 변경하고 ZIP·시트 구조와 저장된 값을 다시 검사한다.
- 단순 데이터 변경을 검증하기 위해 PDF 미리보기를 만들지 않는다.

## 7. Markdown과 설계 문서

- 문서는 현재 유효한 계약을 설명한다. 제거한 기능, 과거 구조와 변경 이력은 사용자가 요청하지 않으면 본문에 남기지 않는다.
- 규칙 하나에는 책임 문서 하나를 정한다. 다른 문서는 내용을 복사하지 않고 링크와 프로젝트별 차이만 기록한다.
- 제목 수준, 코드 펜스, 표, 상대 링크와 파일 경로를 실제 저장소 구조에 맞게 유지한다.
- 구현되지 않았거나 결정되지 않은 정책은 `[TBD]`로 남기고 임의의 값으로 확정하지 않는다.
- 검증을 위한 임시 수치는 `[PROVISIONAL]`로 표시하고 원본 데이터나 설계 문서에서 관리한다.
- 예시 코드가 실제 규칙처럼 오해되지 않도록 예시, 의사 코드와 확정 계약을 구분한다.
- 제품명, 캐릭터명, 실제 타입과 저장소 경로가 필요한 내용은 재사용 문서가 아니라 호스트 프로젝트 적용 문서에 둔다.

## 8. 검증과 완료 보고

### 사용자 검증 지시 우선

- 사용자가 작업 결과의 검증을 금지하거나 보류하면 해당 지시를 기존 문서·작업 지시·완료 기준보다 우선한다. 사용자가 다시 명시적으로 요청하기 전까지 검증을 실행하지 않는다.
- 중단 범위에는 빌드, 테스트, 임시 환경·하네스 실행, UI 실행·캡처, 정적 검사, diff check와 데이터·리소스 대조가 포함된다. 가벼운 확인이나 필수 완료 조건이라는 이유로 임의 예외를 만들지 않는다.
- 요청된 구현·문서·원본 데이터·생성물 변경은 계속 진행한다. 작업에 필요한 파일 읽기와 편집을 별도의 검증 작업으로 확대하지 않는다.
- 총괄은 같은 중단 지시를 모든 담당 작업자에게 전달하고, 이후 배분에서도 검증을 요구하지 않는다.
- 완료 보고에는 변경 내용과 검증 미실시만 간단히 적는다. 실행하지 않은 검증을 성공으로 보고하거나 검증 재개를 반복해서 요청하지 않는다.

아래 검증 절차는 사용자의 검증 중단 지시가 없거나 사용자가 검증을 다시 요청한 범위에서 적용한다.

- 변경한 프로젝트와 직접 의존 프로젝트를 빌드한다.
- 기존 관련 테스트가 있으면 실행한다. 사용자가 요청하지 않았고 호스트 정책에도 없다면 테스트 프로젝트나 테스트 코드를 새로 추가하지 않는다.
- 데이터 생성 작업은 변환기 성공 메시지만 보지 않고 생성 파일, 구문, 참조, 행 수와 필요한 출력 일치를 확인한다.
- 문서 변경은 링크, 경로, 중복된 책임과 오래된 명칭을 검색한다.
- `git diff --check`에 해당하는 변경 검사를 실행하고 저장소의 줄 끝 규칙을 확인한다.
- 완료 보고에는 변경한 계약, 검증 명령과 결과, 아직 수동으로 확인해야 할 항목만 적는다.

## 9. 커밋·푸시 승인과 역할

- 사용자 승인 범위에서 커밋·푸시한다. 같은 작업의 완료 후 커밋·푸시를 미리 승인했다면 철회될 때까지 유지하며 매번 다시 묻지 않는다.
- 커밋만 요청했고 기존 푸시 승인이 없다면 푸시 권한으로 확대하지 않는다. 강제 푸시와 이력 재작성은 별도 승인 범위를 따른다.
- 총괄 게시·작업자 인계 등 호스트의 역할 배분을 우선한다. 공유 작업 트리에서는 승인된 변경 경로와 필요한 신규 파일을 명시해 스테이징한다.
- 검증 중단 지시는 구현·커밋·푸시 중단을 뜻하지 않는다. 추가 검사 없이 승인된 작업을 완료하고 실행하지 않은 검증을 성공으로 보고하지 않는다.

## 10. 호스트 프로젝트 적용 체크리스트

호스트 프로젝트의 코딩 컨벤션 또는 별도 적용 문서에는 최소한 다음 값을 매핑한다.

- 지침 파일과 설계 문서의 우선순위
- C# nullable과 줄 끝 정책
- Unity 또는 서버의 프레임 반복·생명주기 정책
- 데이터 원본, 생성물, 변환 명령과 런타임 조회 방식
- 채택한 재사용 아키텍처 패키지와 적용하지 않는 패키지
- 표준 빌드·검증 명령
- 테스트 추가, 커밋과 배포 권한 정책

매핑되지 않은 항목은 이 문서의 예시를 프로젝트 기본값으로 간주하지 않는다.
