# Deterministic Domain State Machine

> 카탈로그: [재사용 아키텍처](README.md)
> 상태: 프로젝트 독립 이식 기준

---

## 1. 목적

이 패턴은 상태마다 행동과 시간 진행 방식이 다른 도메인 객체를 결정론적으로 실행하고 저장·복원하기 위한 구조다. State Pattern을 프레임워크 라우팅 수단이 아니라 도메인 행동 분리 수단으로 사용한다.

핵심 불변식은 다음과 같다.

1. 도메인 데이터의 최종 소유자는 Owner다.
2. 상태 객체는 생성 직후 실행 가능하다.
3. 복원값은 생성자에서 검증한다.
4. 상태 전환 조건은 도메인 Owner별로 유지한다.
5. 공통 StateMachine은 등록과 Enter·Exit 순서만 재사용한다.
6. 외부에는 상태 enum이 아니라 의미 있는 결과 이벤트를 전달한다.

## 2. 역할

| 구성 요소 | 담당 책임 | 담당하지 않는 책임 |
|---|---|---|
| Owner | 도메인 데이터, 전환 조건, 현재 실행 입력과 이벤트 발생 | 저장 DTO 직렬화와 View 갱신 |
| StateMachine | 상태 등록, 현재 상태, Exit·Enter 전환 절차 | 도메인별 전환 판정과 Tick 계산 |
| State | 현재 상태의 행동과 상태 전용 Tick | Owner 데이터 복제, 외부 이벤트 처리기 소유 |
| Connector | 저장 모델 변환, 실행 호출, 이벤트 투영 | Owner와 State의 직접 상태 변경 |

## 3. 데이터 소유권

Owner는 여러 상태에서 공유되는 실제 도메인 데이터를 한 번만 소유한다. 상태는 자기 상태에만 존재하는 경과 Tick, 남은 Tick과 허용 Tick을 소유할 수 있다.

```text
Owner
├─ 공통 도메인 데이터
├─ 전환 경계
└─ StateMachine
   ├─ State A: A 전용 Tick
   ├─ State B: B 전용 Tick
   └─ State C: C 전용 Tick
```

상태가 Owner의 현재 값 사본을 보관하면 전환 뒤 어느 값이 진실인지 불명확해진다. 공유 데이터는 상태가 Owner의 내부 메서드를 통해 변경한다.

## 4. 완전한 생성과 복원

상태 객체는 생성자가 끝날 때 다음 조건을 만족해야 한다.

- 필수 Owner 참조가 유효하다.
- 허용 Tick과 기간 Tick이 유효하다.
- 저장된 경과·남은 Tick이 허용 범위 안이다.
- 첫 `Execute` 전에 추가 초기화 호출이 필요하지 않다.

`Initialize`, `RestoreElapsedTicks`, `InitializeState`처럼 생성 뒤 불완전한 상태를 보정하는 단계를 두지 않는다.

신규 시작과 복원은 같은 생성자를 사용하거나 같은 불변식을 보장하는 생성자들로 구성할 수 있다. 저장 DTO를 상태가 직접 받지 않고 Connector나 Owner가 원시 값으로 변환해 전달한다.

## 5. Enter와 Exit

`Enter`는 신규 전환과 복원된 최초 진입에 모두 호출된다. 따라서 복원한 Tick을 무조건 0이나 전체 기간으로 초기화하지 않는다.

반복 사용되는 상태는 자기 실행이 끝날 때 `Exit`에서 다음 진입을 위한 런타임 Tick을 초기화한다. 이렇게 하면 최초 복원 진입은 보존되고 정상 전환 뒤 재진입은 새 상태로 시작한다.

상태 객체를 재사용하지 않는 생명주기 상태는 새 상태를 생성해 진입할 수 있다. 이 경우 형식적인 `Exit`와 등록 컬렉션을 강제하지 않는다.

## 6. StateMachine 최소 책임

공통 StateMachine이 제공할 수 있는 기능은 다음으로 제한한다.

- 상태 타입과 상태 객체 일회 등록
- 현재 상태와 상태 타입 보관
- 등록 여부 검증
- 기존 상태 `Exit` 뒤 새 상태 `Enter`
- 같은 상태 객체 중복 전환 무시

도메인별 온도 구간, AI 판단, 날짜 변경과 네트워크 상태를 공통 StateMachine에 넣지 않는다. 서로 다른 Owner가 같은 기반 클래스를 사용해도 전환 원인은 각 Owner에 남는다.

## 7. 두 가지 상태 수명

### 재사용 행동 상태

한 Owner 안에서 같은 상태 인스턴스를 여러 번 오가는 경우다.

- 모든 상태를 한 번 등록한다.
- 상태 전용 Tick은 State가 소유한다.
- 종료 시 `Exit`에서 재진입 값을 준비한다.
- 같은 상태 중복 전환은 실행을 재시작하지 않는다.

### 생명주기 상태

각 상태가 서로 다른 하위 콘텐츠 객체를 소유하고 한 방향으로만 진행하는 경우다.

- 현재 상태와 하위 객체만 생성한다.
- 전환 때 다음 상태와 하위 객체를 새로 만든다.
- 완료 상태가 별도 행동을 갖지 않으면 상태 클래스로 만들지 않는다.
- 활성 상태가 없어진 완료와 실행 상태를 구분한다.

생명주기 상태에 등록형 StateMachine을 강제하면 존재하지 않아야 할 하위 객체를 미리 만들거나 완료 상태를 추가하게 된다.

## 8. 전환 주체

전환 방식은 도메인마다 하나를 선택한다.

- Owner 판정: Owner가 외부 입력을 해석하고 적절한 상태로 전환한 뒤 현재 상태를 실행한다.
- State 완료 요청: 상태가 자기 Tick 종료를 감지하고 Owner의 internal 전환 메서드를 호출한다.

상태가 StateMachine을 직접 참조하거나 임의 상태 enum을 넘기지 않는다. State가 전환을 요청해야 하면 `TransitionToResting`, `EnterNextPhase`처럼 Owner가 허용한 의미 있는 내부 메서드를 호출한다.

## 9. 실행과 이벤트

한 실행 호출에서 전환과 현재 상태 실행 순서를 명확히 한다. 호출자가 사용하지 않는 상태 enum이나 실행 결과를 반환하지 않는다.

상태는 외부 이벤트 처리기를 소유하지 않는다. 상태가 Owner의 변경 메서드를 호출하고 Owner는 변경이 끝난 뒤 의미별 이벤트를 발생시킨다.

```text
Connector.Execute(input)
→ Owner가 전환 판정
→ State.Execute(domainAmount)
→ State가 Owner.ApplyChange 호출
→ Owner가 불변식 보정
→ Owner가 MeaningfulChanged Event 발생
```

여러 결과 이벤트가 필요한 경우 결과 순서를 도메인 규칙으로 고정한다. View 편의를 위해 Owner 상태 Getter를 노출해 다시 읽게 하지 않는다.

## 10. 저장 경계

- 상태 enum만 저장하지 않는다. 복원에 필요한 상태 전용 Tick과 Owner 데이터도 함께 저장한다.
- 서로 다른 상태의 데이터 구조가 다르면 상태별 저장 모델을 분리한다.
- 진행 시간은 도메인의 고정 Tick으로 저장한다. 실제 날짜·시각은 동기화 경계와 분리한다.
- 상태와 StateMachine은 JSON, 프로토콜과 DB 모델을 참조하지 않는다.
- 저장 스냅샷은 실행 객체와 참조를 공유하지 않도록 새 값으로 만든다.

## 11. 필수 테스트

- 신규 상태와 복원 상태가 첫 `Enter` 뒤 올바른 Tick을 유지한다.
- 허용 범위를 벗어난 복원 Tick이 생성자에서 실패한다.
- 같은 상태로의 중복 전환이 Tick을 초기화하지 않는다.
- 정상 종료 후 재진입하면 상태 Tick이 새 값으로 시작한다.
- 상태 우선순위가 경계 입력에서 일관된다.
- 한 실행 호출에서 전환과 실행이 한 번만 일어난다.
- 상태 변경 이벤트가 보정 완료 뒤 정확한 순서로 발생한다.
- 저장 왕복 뒤 같은 입력으로 같은 상태와 결과가 나온다.
- 완료 뒤 추가 입력이 상태를 다시 변경하지 않는다.

## 12. 금지 패턴

- 생성 뒤 별도 복원 메서드로 Tick 덮어쓰기
- StateMachine에 여러 도메인의 전환 조건 추가
- 상태가 Owner 공통 데이터를 복제해 소유
- 상태가 외부 이벤트 처리기와 저장 DTO를 참조
- Controller나 View가 상태를 직접 변경
- 호출자가 사용하지 않는 상태 enum·결과 반환
- 내용 없는 완료 상태 추가
- 비동기 I/O와 프레임워크 수명을 도메인 상태에 결합
