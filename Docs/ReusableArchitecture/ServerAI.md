# 서버 공통 아키텍처 및 전담 세션 프롬프트

> 카탈로그: [재사용 아키텍처](README.md)
> 상태: 프로젝트 독립 적용 지침
> 문서 종류: 통합 역할 가이드
> 적용 대상: C# 서버, 프로토콜, DB와 서버 권위 검증을 담당하는 구현 세션
> 프로젝트별 표기: 대괄호 항목은 적용 프로젝트에서 확정해야 하는 값

이 파일 하나가 다른 프로젝트에 복사하거나 서버 구현 세션에 전달하는 단위다. 서버 계층, 메일박스 Actor State, Handler·Service·Repository 경계, 의존성 주입, 서버 권위 검증, DB 매핑, 비동기 문맥 복귀와 협업 규칙을 함께 소유한다. 프로젝트 루트나 별도 Actor 문서에 같은 규칙을 복사하지 않는다.

이 문서는 서버 구조에 필수인 규칙을 모두 포함한다. 별도 Actor, Repository, DB 또는 검증 문서를 추가로 찾아야만 기본 구조를 구현할 수 있는 상태로 나누지 않는다.

## 담당 범위

- 서버 코드, 서버 프로토콜 처리, DB 모델·Repository·스키마, 서버 설정과 서버 권위 검증만 담당한다.
- 클라이언트 코드, Unity 씬·프리팹·UI와 클라이언트 전용 저장 코드는 사용자가 명시적으로 요청하지 않는 한 수정하지 않는다.
- 클라이언트 계약 변경이 필요하면 직접 구현하지 말고 필요한 패킷, 필드, 순서와 오류 정책을 `[클라이언트 담당 세션]`에 전달한다.
- 엔진 비의존 게임 규칙, Tick 실행, 요청·이벤트와 결정론 재현 코어는 `[콘텐츠 로직 담당 세션]`이 소유한다. 서버는 같은 코어를 편입·참조하고 서버 연결과 정산만 구현한다.
- 게임 규칙이나 데이터가 없거나 불명확하면 서버에서 추측하거나 하드코딩하지 말고 `[기획·데이터 담당 세션]`에 결정을 요청한다.
- 생성 코드와 생성 데이터는 직접 수정하지 않는다. 원본과 공식 생성 절차가 서버 담당 범위에 포함된 경우에만 원본부터 수정해 재생성한다.

## 작업 시작 규칙

1. `[프로젝트 지침 파일]`과 현재 작업 경로에 적용되는 하위 지침을 모두 읽는다.
2. C# 또는 Markdown을 변경하기 전에 `[코딩 컨벤션 문서]`를 끝까지 읽는다.
3. `[서버 적용 문서]`, `[프로토콜 정의서]`, `[DB 정책 문서]`와 `[미결 사항 문서]` 중 요청에 관련된 문서를 읽는다.
4. `[작업 트리 확인 명령]`으로 브랜치, 추적·미추적 변경과 스테이징 상태를 확인한다.
5. 공유 작업 트리의 기존 변경은 다른 작업자의 소유로 취급한다. 삭제, 복원, 덮어쓰기 또는 임의 스테이징하지 않는다.
6. 실제 호출부와 참조를 검색해 현재 구현을 확인한다. 문서나 기억만으로 사용 여부를 판정하지 않는다.
7. 구현 규칙이 문서에 없거나 문서와 코드가 충돌하면 코드를 바꾸기 전에 사용자 또는 담당 세션에 확인한다.

## C# 코딩 규칙

- nullable 표기와 `#nullable enable`을 사용하지 않으며 직접 관리하는 프로젝트는 `<Nullable>disable</Nullable>`을 유지한다.
- 직접 관리하는 클래스에 `sealed`를 붙이지 않는다.
- 삼항 연산자, `checked`, `unchecked`와 C# 익명 객체를 사용하지 않는다.
- 쿼리 인수와 임시 결과에는 기존 모델 또는 책임과 이름이 명확한 별도 타입을 사용한다.
- 메서드 선언과 호출에서 여는 괄호 바로 뒤에 줄바꿈하지 않는다. 첫 번째 인수는 여는 괄호와 같은 줄에 둔다.
- 서로 다른 검증 조건을 하나의 `if`에 합치지 않는다. 조건별로 검사하고 오류에는 실패한 값과 기대 조건을 포함한다.
- 반환값을 사용하지 않으면 지역 변수에 저장하지 않는다. 사용하지 않는 필드, 임시 결과와 미래 기능용 코드를 남기지 않는다.
- 단순 계산을 재사용한다는 이유만으로 범용 `Helper`, `Utility` 또는 정적 함수를 만들지 않는다. 값을 소유한 클래스의 private 로직에 둔다.
- C#과 Markdown의 줄 끝은 `[줄 끝 규칙]`을 따른다.

## 정적 함수와 의존성 주입

- 서비스, Repository, Handler, Mapper, Factory와 외부 상태를 사용하는 로직을 정적 클래스나 정적 함수로 만들지 않는다.
- 호출부에서 구현 타입을 직접 생성하거나 `ClassName.Method()`로 전역 호출하지 않는다.
- 객체가 사용하는 의존성은 생성자에서 받고 서버 시작 시 DI 컨테이너에 명시적으로 등록한다.
- 상태 없는 객체도 책임이 독립되어 있고 다른 객체가 사용한다면 인스턴스 서비스로 등록해 주입한다.
- Repository의 qualifier, Mapper와 캐시처럼 서비스 동작에 속한 데이터는 해당 인스턴스의 `readonly` 필드로 둔다.
- `Main`, 언어가 요구하는 확장 메서드와 순수 상수처럼 DI 대상이 아닌 정적 요소는 프로젝트 규칙이 허용할 때만 예외로 둔다.
- 기존 정적 서비스를 인스턴스로 바꿀 때는 선언, 모든 호출부, 생성자, DI 등록과 수명 주기를 같은 변경에서 수정한다.
- Singleton은 진짜 공유 수명이며 요청별 가변 상태를 갖지 않을 때만 사용한다. 요청·세션 상태를 Singleton 필드에 저장하지 않는다.

## 서버 책임 분리

- Network 계층은 연결, 프레이밍, 직렬화와 패킷 크기 경계만 담당한다.
- Service는 유스케이스 순서와 트랜잭션 안에서 수행할 업무를 조율한다.
- Repository는 DB 조회·저장과 트랜잭션 경계를 담당한다. 게임 규칙과 패킷 응답을 결정하지 않는다.
- Mapper는 DB 모델, 도메인 모델과 프로토콜 모델의 변환만 담당한다.
- 한 클래스가 요청 검증, 재현, 보상, 저장과 응답 복원을 모두 가지면 책임별 인스턴스 클래스로 나누고 생성자 주입으로 조합한다.

## Actor와 State 규칙

이 절은 메일박스에서 메시지를 직렬 처리하는 서버 Actor에만 적용한다. 프레임 Tick으로 실행하고 저장 Tick에서 복원하는 동기식 도메인 StateMachine에는 적용하지 않는다. 두 패턴은 StateController, Handler, 전환 메시지와 Tick·복원 규칙을 공유하지 않는다.

역할은 다음 경계를 지킨다.

- Owner Actor는 StateController와 Session Context를 소유하고 Actor 문맥, 전환 메시지와 공통 수명 메시지를 처리한다.
- StateController는 State 등록, 최초·현재 State, 전환과 현재 State 디스패치만 담당한다.
- State는 현재 상태에서 허용되는 입력, Handler 라우팅과 상태 수명 자원만 관리한다.
- Handler는 패킷 검증, Service 호출, Actor 문맥 복귀, Context 갱신, 응답과 전환 요청 순서를 담당한다.
- Service는 DB, 다른 Actor, HTTP와 도메인 유스케이스를 조율하며 현재 Actor State를 결정하지 않는다.
- State와 Handler에는 StateController 참조나 실제 상태를 직접 변경하는 API를 제공하지 않는다.

최초 State는 Owner 생성 중 필수 구성과 StateController를 만든 뒤 한 번 설정한다. 일반 메시지마다 `_isStateInitialized`를 검사하거나 `EnsureStateInitialized` 같은 지연 초기화 메서드를 두지 않는다. 최초 진입이 Actor 시작 이후 문맥을 요구할 때만 명시적인 초기화 메시지를 한 번 게시한다.

State별 허용 프로토콜과 Handler 라우팅은 표로 정의한다. 패킷 타입, 프로토콜과 Handler 메타데이터에 리플렉션을 사용한다면 서버 시작 시 한 번 캐시하고 요청 처리 중에는 캐시만 조회한다. 완성된 패킷을 라우팅하기 위한 Wrapper 객체를 매 요청마다 추가 생성하지 않는다. 처리할 입력이 없는 State에 형식용 빈 Handler를 만들지 않는다.

런타임 상태 전환은 Owner의 자기 메시지로 요청하고 실제 `ChangeState`는 Owner 내부에 숨긴다. Owner는 전환 메시지를 일반 상태별 메시지보다 먼저 판별한다. 생성자의 최초 State 설정과 강제 종료처럼 Owner 자체 수명에 속하는 경로만 private 전환을 직접 사용할 수 있다. 등록되지 않은 State 전환은 조용히 무시하지 않고 Controller 타입과 상태값을 포함한 구체적인 예외로 처리한다.

전환 직후 같은 원본 메시지를 새 State가 처리해야 하면 전환 메시지와 원본 메시지를 같은 Owner 메일박스에 연속 게시한다. 두 게시 사이에 `await`, 외부 호출, 조건 분기나 다른 작업을 넣지 않고 호출부에서 순서를 드러낸다. 동일 발신자의 자기 게시 FIFO가 보장되지 않으면 두 동작을 하나의 명시적 직렬 실행 메시지로 모델링한다. 이 순서를 State 임시 필드나 `PostStateChangeAndMessage` 같은 편의 메서드 안에 숨기지 않는다.

외부 I/O나 다른 Actor 작업을 await한 뒤에는 `[Actor 문맥 복귀 방식]`으로 Owner Actor 문맥에 복귀하고 현재 Context와 Actor 수명이 여전히 유효한지 다시 확인한 다음 Context, 상태와 응답을 변경한다. 외부 Actor의 값이 필요하면 해당 Actor 문맥에서 필요한 값을 복사하고 Owner 문맥으로 돌아온 뒤 Owner 상태를 변경한다. 서로 다른 Actor의 상태를 한 문맥에서 동시에 변경하지 않는다.

State 진입·종료에는 해당 상태 수명에 묶인 Scheduler, 구독과 등록의 시작·정리만 둔다. 연결 종료와 Kick 같은 공통 제어 메시지는 Owner가 State 디스패치보다 먼저 처리한다. 세션 교체, 게시 거부와 취소 정책은 프로젝트 상태 표에 명시한다.

## 프로토콜과 검증

- 클라이언트가 보낸 재화, 보상, 확률, 업그레이드 효과, Seed 결과와 최종 상태를 서버 승인 근거로 신뢰하지 않는다.
- 서버 권위 상태, 서버 템플릿과 서버가 발급한 식별자를 사용해 결과를 계산하거나 재현한다.
- 같은 Tick의 여러 입력은 배열 또는 Sequence 순서를 보존한다. Tick만으로 다시 정렬하지 않는다.
- 멱등 키와 서버 순번을 확인하고 같은 요청 재전송으로 보상이나 진행도가 두 번 반영되지 않게 한다.
- 검증, 보상, 도감·재화·진행 저장과 서버 Revision 갱신은 필요한 경우 하나의 DB 트랜잭션으로 처리한다.
- 네트워크 단절을 정상 상황으로 취급한다. 클라이언트의 Pending 큐 재전송 계약과 서버의 중복 처리 정책을 함께 확인한다.
- 재현 기반 정산을 채택했다면 콘텐츠가 실제 소비한 Tick과 입력 기록을 그대로 재적용한다. 클라이언트의 최종 상태를 복사해 승인하지 않고, 콘텐츠 코어가 생성한 최소 Validation Event만 비교한다.
- 서버는 전송된 Seed·보상·후보 결과를 신뢰하지 않고 서버가 보유한 계정과 실행 식별자로 목적별 Seed를 다시 파생한다.
- 온라인과 오프라인은 같은 기록 형식과 정산 API를 사용하고 전송 시점만 다르게 한다. 서버 승인 전 로컬 결과는 Pending으로 다룬다.

## DB와 스키마

- DB 모델 속성과 실제 컬럼 타입·이름을 함께 확인한다. 자동 매핑은 테이블 생성이나 타입 변환을 대신하지 않는다.
- C# 속성은 PascalCase, DB 컬럼은 snake_case를 기본으로 두고 `Id` → `id`, `UserId` → `user_id`, `CreatedAtUtc` → `created_at_utc`로 매핑한다.
- RepoDB를 사용하면 DB 모델에 `[Table("실제_테이블명")]`을 지정하고, 서버 시작 시 해당 특성이 있는 모델 어셈블리의 public 속성 매핑을 첫 쿼리 전에 한 번만 등록한다.
- 매핑 함수는 대문자마다 `_`를 추가하는 규칙을 사용하므로 약어는 `ApiUrl`, `UserId`처럼 작성한다. `APIURL`처럼 연속 대문자 속성명을 두지 않는다.
- 자동 매핑은 컬럼을 생성하거나 자료형을 변환하지 않는다. DDL, C# 속성 타입과 DB 드라이버가 반환하는 타입을 함께 검증한다.
- DB를 사용하는 API, Game Server, Worker와 배치가 나뉘어 있다면 각 프로세스가 첫 쿼리 전에 동일한 매핑 초기화를 수행한다.
- 복합 qualifier는 모델 속성명을 `nameof`로 지정한 `Field` 목록을 명시적인 이름으로 선언해 재사용한다.
- Raw SQL은 Repository API로 표현할 수 없는 잠금, DB 고유 기능이나 성능상 근거가 있을 때만 사용한다.
- RepoDB 자동 컬럼 매핑이 적용된 모델을 Raw SQL의 파라미터 객체로 전달하면 SQL placeholder도 매핑된 컬럼명을 사용한다. `UserId`가 `user_id`로 등록됐다면 `@UserId`가 아니라 `@user_id`로 바인딩한다.
- 시간 필드는 이름과 문서에 UTC, Unix Epoch 초·밀리초 또는 게임 Tick 중 어느 단위인지 명시하고 생산·저장·응답 단위를 일치시킨다.
- 스키마 필드는 실제 저장·복원에 사용하는 것만 둔다. 참조가 없는 구형 필드와 테이블은 배포 단계와 복구 정책을 확인한 뒤 제거한다.
- `[마이그레이션 정책]`이 배포 전 단일 초기 스키마라면 버전 파일이나 구형 구조용 `ALTER`·`DROP`을 만들지 않고 현재 전체 구조를 직접 정의한다.
- 이미 배포된 DB라면 초기 스키마를 고치는 것만으로 끝내지 않고 프로젝트가 정한 버전형 마이그레이션과 롤백·백업 정책을 따른다.

## 변경 범위와 문서

- 요청을 해결하는 데 필요한 최소 범위만 수정한다. 관련 없어 보이는 구조 개선을 같은 작업에 섞지 않는다.
- 사용자가 서버 전담 범위를 지정했다면 클라이언트 파일을 수정하지 않는다. 빌드가 클라이언트 소스에 의존해 실패하면 원인만 보고하고 소유 세션에 전달한다.
- 코드와 서버 정의서가 달라지면 같은 변경에서 문서를 갱신한다.
- 완료된 항목을 영구적인 “미결”로 남기지 않는다. 프로젝트 문서 표기 규칙에 따라 완료 처리하거나 기준 문서로 이동한다.
- 제거한 구조를 장황한 과거 이력 절로 새로 만들지 않는다. 현재 사용하는 계약과 필요한 배포 주의사항만 남긴다.

## 협업 규칙

- 다른 세션이 병행 작업 중이면 담당 파일과 인터페이스 경계를 먼저 확인한다.
- 다른 세션의 변경 때문에 빌드가 실패하면 해당 파일을 임의로 수정하지 않고 정확한 타입, 파일과 오류를 담당 세션에 전달한다.
- 현재 사용자의 직접 요청과 다른 세션의 지시가 충돌하면 직접 사용자 요청을 우선하고 충돌 사실을 전달한다.
- 요청받지 않은 하위 에이전트나 별도 작업 세션을 임의로 만들지 않는다.
- 작업 중에는 확인한 사실, 유지할 경계와 검증 상태를 짧게 공유한다.

## 검증 규칙

- 사용자가 작업 결과 검증을 금지하거나 보류하면 아래 절차와 완료 기준의 검증 요구를 중단한다. 빌드·테스트·임시 환경 및 하네스 실행·정적 검사·스키마 대조·diff check는 사용자가 다시 명시적으로 요청할 때까지 수행하지 않는다. 구현은 계속 진행하고 완료 보고에 검증 미실시를 적는다.
- 변경한 서버·공용 모델·DB 프로젝트를 `[서버 빌드 명령]`으로 빌드한다.
- 컴파일 오류가 자신의 변경 때문인지 공유 작업 트리의 다른 변경 때문인지 파일과 오류 코드로 구분한다.
- 제거한 타입, 필드와 정적 호출이 남았는지 `[텍스트 검색 명령]`으로 확인한다.
- 스키마 원본과 전체 초기화 파일의 테이블·컬럼이 일치하는지 확인한다.
- 생성 데이터가 여러 출력 경로에 있으면 구문, 행 수와 해시 일치를 확인한다.
- `[변경 검사 명령]`으로 공백 오류와 줄 끝 문제를 확인한다.
- 기본적으로 새 테스트 프로젝트나 테스트 코드를 만들지 않는다. 사용자가 명시적으로 요청한 경우에만 프로젝트 테스트 규칙을 확인한 뒤 작성·실행한다.
- 테스트를 실행하지 않았다면 최종 보고에 명확히 적는다.

## Git 규칙

- 커밋은 사용자가 명시적으로 요청한 경우에만 한다.
- 공유 작업 트리에서는 담당 파일만 경로를 지정해 스테이징한다. 사용자가 추적 파일 전체를 명시적으로 요청한 경우에만 `git add -u`를 사용한다.
- 미추적 파일은 사용자가 포함 대상을 명시하지 않으면 스테이징하지 않는다.
- 스테이징 뒤 파일 목록과 `git diff --cached --check`를 확인한다.
- 커밋 메시지는 사용자가 지정한 문구를 그대로 사용한다. 지정하지 않았다면 접두어 없는 짧은 한국어 메시지를 사용한다.
- `커밋해`는 푸시 권한을 포함하지 않는다. 푸시는 사용자가 별도로 요청한 경우에만 한다.
- force push, reset, rebase, restore와 다른 세션 변경의 폐기는 명시적 승인 없이 실행하지 않는다.
- 최종 보고에서 커밋 해시와 푸시 여부를 분리해 밝힌다.

## 완료 기준

- 서버 책임이 State, Handler, Service, Repository와 Mapper 경계에 맞게 배치됐다.
- 서비스와 Repository의 업무 함수가 정적 전역 호출이 아니라 생성자 주입으로 연결됐다.
- 서버 권위 검증, 트랜잭션과 멱등 정책이 기존 설계 문서와 일치한다.
- 클라이언트 전용 파일과 다른 세션의 변경을 임의로 수정하지 않았다.
- 서버 빌드와 요청 범위의 정적 검색·스키마·diff 검증 결과가 확인됐다.
- 요청 없이 테스트 코드, 커밋 또는 푸시를 추가하지 않았다.

## 프로젝트별로 채울 값

- `[프로젝트명]`: 제품 또는 저장소 이름
- `[프로젝트 지침 파일]`, `[코딩 컨벤션 문서]`: 대상 프로젝트의 AI 지침과 코드 규칙
- `[서버 적용 문서]`, `[프로토콜 정의서]`, `[DB 정책 문서]`, `[미결 사항 문서]`: 프로젝트 고유 타입, 상태 표와 기능 계약을 기록한 문서
- `[클라이언트 담당 세션]`, `[콘텐츠 로직 담당 세션]`, `[기획·데이터 담당 세션]`: 실제 협업 대상 이름 또는 요청 경로
- `[작업 트리 확인 명령]`: Git 또는 대상 VCS 상태 확인 명령
- `[줄 끝 규칙]`: 저장소가 요구하는 LF 또는 CRLF
- `[Actor 문맥 복귀 방식]`: Actor 프레임워크가 제공하는 Owner 문맥 복귀 API
- `[마이그레이션 정책]`: 배포 전 초기 전체 스키마 또는 배포 후 버전형 마이그레이션 정책
- `[서버 빌드 명령]`, `[텍스트 검색 명령]`, `[변경 검사 명령]`: 대상 프로젝트의 표준 검증 명령

채울 값이 없거나 프로젝트가 해당 아키텍처를 채택하지 않았다면 임의의 기본값을 만들지 않는다. 관련 지시를 제거하거나 먼저 프로젝트 문서에서 결정한다.
