# 재사용 아키텍처 카탈로그

이 폴더는 특정 제품과 저장소에 종속되지 않는 규칙과 적용 가이드를 관리한다. 호스트 프로젝트의 게임 규칙, 타입 이름, 파일 경로, 밸런스 값과 현재 구현 현황은 넣지 않는다.

## 문서 종류

| 종류 | 제공하는 것 | 제공하지 않는 것 |
|---|---|---|
| 공통 컨벤션 | 여러 저장소에서 반복하는 작업 방식, C#·Markdown·생성물 규칙 | 호스트 프로젝트의 실제 경로·도구 명령·채택 정책 |
| 아키텍처 패키지 | 특정 문제의 불변식, 책임 경계, 적용 순서와 검증 기준 | 호스트 프로젝트의 실제 타입·경로·현재 구현 상태 |
| 역할 가이드 | 담당 범위, 협업 방식, 시작 절차와 완료 보고 형식 | 프로젝트가 채택하지 않은 아키텍처 규칙과 구현 세부 |

역할 가이드만으로 기술 구조를 결정하지 않는다. 대상 프로젝트가 아키텍처 패키지를 채택했다면 역할 가이드와 함께 전달하고, 채택하지 않았다면 해당 규칙을 역할 프롬프트에 섞지 않는다.

## 검증 실행 정책

사용자가 작업 결과 검증을 금지하거나 보류하면 카탈로그와 역할 가이드의 검증·완료 기준보다 그 지시를 우선한다. 사용자가 다시 명시적으로 요청하기 전까지 총괄과 담당 작업자 모두 추가 검증을 실행하지 않는다. 공통 규칙은 [사용자 검증 지시 우선](CodingConvention.md#사용자-검증-지시-우선)을 따른다.

### 공통 컨벤션

| 문서 | 적용 대상 | 핵심 내용 |
|---|---|---|
| [`CodingConvention`](CodingConvention.md) | C#·Unity·Markdown 저장소 | 작업 범위, C# 표현, 시간·난수, 생성 데이터, 문서와 검증 기준 |
| [`ReleasePolicy`](ReleasePolicy.md) | 단일 실행 파일 배포를 지원하는 데스크톱 앱 | 실행 파일 하나에 필수 런타임·데이터·설정 포함, 게시와 다운로드 안내 |

### 아키텍처 패키지

| 패키지 | 적용 대상 | 핵심 내용 |
|---|---|---|

| [`DomainStateMachine`](DomainStateMachine.md) | 동기식·결정론적 도메인 로직 | 완전한 상태 생성, Tick 복원, Owner 중심 전환과 재사용 상태·생명주기 상태 구분 |

## 배치 원칙

- 모든 재사용 문서를 카탈로그 루트에 평탄하게 둔다. 역할·패키지 구분은 폴더가 아닌 카탈로그 표가 소유한다.
- 진입 문서는 영문 PascalCase `<UnitName>.md`로 둔다. 상세 규칙이 필요할 때만 같은 위치에 `<UnitName>Architecture.md`를 추가하고 진입 문서에서 연결한다.
- 같은 단위의 진입 문서를 두 곳에 복제하거나 단위 이름이 없는 `ARCHITECTURE.md` 파일을 만들지 않는다.
- 이 카탈로그는 프로젝트 독립 규칙과 이식 체크리스트만 소유한다.
- 호스트 프로젝트의 나머지 설계 문서는 선택한 규칙을 실제 타입·정책·구현 위치에 매핑한다.
- 범용 문서에는 특정 캐릭터, 재화, 프로토콜 enum과 데이터 ID를 넣지 않는다.
- 프로젝트 적용 문서는 범용 문서를 복사해 변형하지 않고 링크한 뒤 차이만 기록한다.
- 구현과 규칙이 다르면 범용 규칙을 현재 코드에 맞춰 낮추지 않는다. 적용 문서에 차이를 명시하고 구현 미결로 추적한다.

```text
ReusableArchitecture/
├─ README.md
├─ CodingConvention.md
├─ <UnitName>.md
└─ <UnitName>Architecture.md
```

## 다른 프로젝트 세션에 전달하는 기준

이 카탈로그 전체를 역할 프롬프트처럼 한꺼번에 전달하지 않는다. 해결할 문제가 패키지의 적용 대상과 일치할 때 해당 패키지만 선택한다.

1. 역할을 맡길 때는 필요한 역할 가이드 하나를 고른다.
2. 대상 프로젝트가 공통 컨벤션을 채택했다면 `CodingConvention.md`와 프로젝트 적용 문서를 함께 전달한다.
3. 해결할 기술 문제가 아키텍처 패키지의 적용 대상과 일치할 때만 해당 패키지를 추가한다.
4. 카탈로그에 연결된 `<UnitName>.md`를 먼저 전달하고, 그 문서가 지정한 `<UnitName>Architecture.md`가 있으면 함께 전달한다.
5. 대상 프로젝트의 `AGENTS.md`, 코딩 컨벤션, 구조 문서와 작업 요청을 같이 전달한다.
6. 대상 프로젝트 세션은 구현 전에 `[PROJECT-SPECIFIC]` 항목과 `프로젝트별로 바꿀 것`을 프로젝트 설계 문서에 매핑한다.
7. 실제 타입, 경로, 패킷, 데이터 ID, 밸런스와 현재 구현 상태는 대상 프로젝트 문서와 저장소에서만 결정한다.
8. 범용 문서와 대상 프로젝트 규칙이 충돌하면 대상 프로젝트 규칙을 우선하고 차이와 채택 결정을 적용 문서에 기록한다.
9. 적용 조건을 만족하지 않거나 프로젝트 매핑이 비어 있으면 범용 문서를 구현 지시로 사용하지 않는다.

| 문제 | 전달할 문서 | 선택하지 않는 경우 |
|---|---|---|
| 여러 저장소에 같은 C#·Markdown·생성물 작업 규칙 적용 | `CodingConvention`과 호스트 적용 문서 | 호스트 규칙이 별도이고 이 컨벤션을 채택하지 않은 프로젝트 |
| 메일박스 Actor의 입력 허용 상태와 비동기 전환 | `ActorState` | 동기식 Tick 도메인 상태 |
| 결정론적 도메인 상태와 저장·복원 | `DomainStateMachine` | 네트워크 Actor의 메시지 라우팅 |
| 클라이언트 예측, 서버 재현과 권위 정산 | `ReplayValidationSync` | 서버 재현이나 오프라인 Pending이 없는 단순 저장 |
| RepoDB 모델과 snake_case 컬럼 연결 | `RepoDbSnakeCaseMapping` | RepoDB를 사용하지 않거나 명시적 컬럼 매핑을 사용하는 프로젝트 |
| Unity Domain·Presenter·Model·View 책임과 UI 문자열 경계 | `UnityClientArchitecture`와 `UnityClientAI` | 다른 UI 아키텍처를 이미 표준으로 사용하는 프로젝트 |
| Unity 외부 에셋 동적 로드와 반복 프리팹 풀링 | `UnityDynamicResourcePooling`과 `UnityClientAI` | Addressables 등 다른 로드·풀 표준을 사용하는 프로젝트 |
| 기획 문서와 원본 데이터 담당 역할 | `GameDesignDataAI` | 코드 구현만 담당하는 세션 |
| Unity 화면·씬·프리팹과 클라이언트 연결 담당 역할 | `UnityClientAI` | 엔진 비의존 로직이나 서버 구현 세션 |
| C# 서버, 프로토콜, DB와 서버 권위 검증 담당 역할 | `ServerAI` | 클라이언트 화면 구현이나 기획·데이터 전담 세션 |

## 전달 메시지 필수 항목

다른 프로젝트 세션에는 문서 링크만 보내지 않고 다음 항목을 한 메시지에 포함한다.

- 맡길 역할과 이번 작업 범위
- 선택한 역할 가이드
- 채택한 아키텍처 패키지와 선택 이유
- 대상 프로젝트의 지침·구조·데이터·미결 문서
- `[PROJECT-SPECIFIC]` 매핑값 또는 매핑을 기록할 문서
- 수정하면 안 되는 영역과 다른 담당자 소유 파일
- 완료 판단에 사용할 빌드·테스트·수동 검증

역할 가이드와 아키텍처 패키지에 없는 프로젝트 규칙을 범용 규칙처럼 추가하지 않는다. 필요한 프로젝트 전용 지시는 대상 프로젝트의 `AGENTS.md`나 적용 문서에 둔다.

범용성 검사는 간단하다. 패키지 안의 문장을 적용하려면 특정 제품명이나 저장소 경로를 알아야 한다면 그 문장은 범용 문서가 아니라 호스트 프로젝트의 적용 문서에 둔다.

## 새 재사용 단위 추가 기준

다음 조건을 모두 만족할 때만 새 재사용 문서나 패키지를 추가한다.

1. 둘 이상의 프로젝트에서 같은 문제와 책임 경계가 반복될 수 있다.
2. 특정 게임 규칙과 데이터 없이 설명할 수 있다.
3. 적용 조건, 바꿔야 할 지점과 검증 방법을 문서화할 수 있다.
4. 기존 패키지의 한 절로 충분하지 않은 독립적인 생명주기나 기술 경계를 가진다.

문서 파일명은 영문 PascalCase로 작성한다. 아키텍처 패키지는 `<UnitName>.md`에 적용 대상, 전달 단위와 적용 순서를 적고 상세 규칙이 필요할 때만 `<UnitName>Architecture.md`를 추가한다. 역할 가이드는 담당 범위, 프로젝트별 입력값, 협업 규칙, 검증과 완료 보고 형식을 포함한다.
