# 저장소별 Git 작업 큐

## 범위

여러 화면의 `IsBusy`는 진행 상태를 표시하는 데 계속 쓸 수 있지만, 사용자가 실행한 Git 작업을 아무 표시 없이 버리는 입구가 되면 안 된다. 공통 큐는 **저장소 상태를 바꾸는 사용자 명령 단위**에서 적용한다. `GitCommandRunner`의 개별 프로세스마다 큐를 걸지 않는다. 브랜치 전환처럼 한 동작이 여러 Git 명령과 후속 상태 조회를 포함해도 한 작업으로 취급한다.

앱에는 DI Singleton 작업 조정자를 하나 두고, 저장소 루트별로 `Dignus.Collections.ArrayQueue`와 단일 `async Task` 소비 루프를 유지한다. 같은 저장소의 변경 작업은 한 번에 하나씩 실행하되 서로 다른 저장소의 작업은 독립적으로 진행한다. 큐는 메모리에서만 유지하며 별도 스레드·폴링 타이머·Git 프로세스를 만들지 않는다. History, diff, 상태 조회 같은 읽기 작업은 공통 큐에서 기다리지 않고 기존 취소·최신 응답 판별을 사용한다. 따라서 모든 Git 작업을 앱 전역 한 줄에 세우지 않는다.

전역 Git 설정처럼 특정 저장소에 속하지 않는 변경은 하나의 고정된 전역 설정 작업 키로 직렬화한다. 저장소 로컬 설정은 해당 저장소 루트의 큐를 사용한다.

`ArrayQueue`에는 `Add`/`Read`/`TryRead`를 사용한다. 큐 조작과 소비 루프 시작 여부만 짧게 동기화하고, 사용자 명령을 실행하는 `await` 동안 잠금을 잡지 않는다. 각 요청은 기다릴 수 있는 `Task`를 돌려주며 성공·실패·취소를 호출자에게 전달한다. 큐 내부에서 같은 저장소 큐에 다시 등록해 기다리지 않도록, 호출 경계는 ViewModel의 최상위 변경 명령으로 한정한다.

## 입력 정책

- 브랜치 전환 요청도 입력한 순서대로 FIFO로 실행한다. `A` 실행 중 `B`, 다시 `A`를 요청했다면 명시적으로 취소하지 않는 한 세 요청을 모두 처리한다. 현재 브랜치와 같은 대상이 차례가 됐을 때만 Git 전환 명령 없이 그 요청을 완료한다. 단일 클릭은 선택만 하고 더블클릭·우클릭 메뉴에서만 요청한다.
- Stage/Unstage, Commit, Stash, Reset, Discard, Fetch/Pull/Push, 태그 생성, 저장소별 Git 설정 변경 등은 실행 시점의 저장소·대상·상태를 다시 확인한다. 이미 사라졌거나 바뀐 대상은 실행하지 않고 이유를 표시한다. 확인 창이 필요한 폐기·Hard reset 등의 승인 범위를 큐에서 넓히지 않는다.
- 커밋·폐기 등도 이미 입력한 요청은 임의로 합치거나 버리지 않는다. 실행 차례에 선행 작업으로 대상이 사라졌다면 이유를 표시하고 그 요청을 완료한다. `busy`를 거절 이유로 사용하지 않는다.
- 큐에 넣어야 할 명령은 `CanExecute`나 메뉴의 `IsEnabled`가 다른 Git 작업의 `IsBusy` 때문에 꺼지지 않아야 한다. 저장소·대상 누락이나 승인 취소처럼 입력 자체가 성립하지 않는 이유는 구분해서 처리한다.
- 각 화면은 실행 중 대상과 대기 중 작업 수를 보여 준다. 저장소를 바꿔도 이미 넣은 요청은 원래 저장소의 큐에서 계속 처리한다. 명시적인 취소 요청에서만 대기 작업을 취소하고, 기존 실행 중 작업의 결과가 새 저장소 화면을 덮지 않게 한다. Git 명령 실패는 해당 요청에 전달한다.
- 큐 요청에 전달하는 취소 토큰은 사용자가 해당 작업을 중단한 경우에만 취소한다. 화면의 조회 취소 토큰이나 저장소 전환 버전은 대기 작업의 취소 신호로 재사용하지 않는다.

## 적용 순서

먼저 공통 조정자의 계약과 DI 수명을 마련한다. 각 작업자가 소유한 ViewModel의 **변경 명령 입구**를 순서대로 연결한다. 읽기 작업이나 단순 UI 입력·설정 저장까지 모두 큐에 넣지 않는다. 기존 브랜치 전환의 마지막 대상 보류 로직은 FIFO 큐로 교체한다. `RequestNewBranchAsync`의 창 내부 큐는 공통 조정자와 역할이 겹치는 부분만 정리한다.
