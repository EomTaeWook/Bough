# 정식 릴리스 기반 앱 업데이트

## 대상과 진입

설정에 Bough의 현재 버전과 **업데이트 확인**, 새 버전이 준비되면 **업데이트 후 재시작**을 제공한다. 사용자가 버튼을 눌렀을 때 조회·다운로드하며 시작 시 자동 설치나 예약 설치는 추가하지 않는다. 저장소를 열지 않아도 사용할 수 있는 앱 설정이다.

업데이트 원본은 공식 `EomTaeWook/Bough` GitHub Releases로 고정한다. 사용자 작업 저장소·브랜치·Git 인증 계정 설정을 업데이트 원본으로 사용하지 않는다.

## 화면 배치와 릴리스 페이지

- 설정의 버튼 순서는 업데이트 확인 → 업데이트 후 재시작 → 릴리스 페이지 → 취소다. 취소는 기존 취소 가능 조건에서 표시한다.
- 재시작 옆의 릴리스 페이지 버튼은 업데이트 확인 전에도 표시한다. 공식 [GitHub 릴리스 목록](https://github.com/EomTaeWook/Bough/releases)을 OS 기본 브라우저로 열며 조회 성공·정식 후보·ReleaseUrl 값을 요구하지 않는다.
- 다운로드 용량 안내는 설정에 남기고 진행 막대는 기존 왼쪽 하단 3px 막대를 사용한다. 전체 크기를 알면 실제 비율, 모르면 무한 진행을 표시한다.
- 왼쪽 하단에는 진행 막대만 표시하고 릴리스 페이지는 설정의 재시작 옆 버튼에서 연다. 다운로드 종료·실패·취소 뒤에는 기존 Git·메인 진행 표시로 복귀한다.
- Main은 기존 AppUpdateViewModel의 다운로드 상태·byte 값을 읽으며 별도 진행 상태를 복제하지 않는다. 부모 Git busy와 원격 팝업 중복 진행 억제는 유지하고 창 종료 때 표시 구독을 해제한다.
- 페이지 열기 실패는 기존 코드·원본 예외·현재 언어 표시 경로를 사용한다. 페이지 열기는 업데이트 조회나 설치를 실행하지 않는다.

## 정식 버전만 선택

- 게시된 정식 릴리스만 후보로 사용하고 `draft`와 `prerelease`는 제외한다. 베타 포함 설정은 제공하지 않는다.
- GitHub의 [정식 최신 릴리스 API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)를 사용하되 응답의 정식 여부와 버전도 확인한다. 정식 릴리스가 없는 404는 조회 오류와 구분해 안내한다.
- 현재 앱의 실제 배포 버전과 후보를 비교한다. 높은 정식 버전만 업데이트하며 같은 정식 버전이나 이전 버전으로 바꾸지 않는다. 현재 버전이 베타이고 같은 숫자의 정식 버전이 게시되면 정식 버전을 새 후보로 취급한다.
- 현재 버전·최신 정식 버전·조회 상태와 필요한 오류를 설정에서 표시한다. 실패를 최신 버전이라고 표시하지 않으며 번역 원본은 언어 변경 때 다시 표시한다.

베타 허용은 사용자가 승인한 이번 격리 테스트 사본에만 적용한다. 테스트에서 베타를 조회·다운로드한 사실을 제품의 배포 채널 변경으로 해석하지 않는다. 제품 소스·문구·문서는 정식 전용 정책을 유지하며 테스트용 채널 설정이나 분기를 제품에 추가하지 않는다.

## 다운로드와 보관

Windows x64 단일 실행 파일 asset을 선택해 전용 임시 위치에 다운로드한다. 고정한 릴리스·asset 정보를 사용하며 실행 중인 파일에는 다운로드하지 않는다. 다운로드와 해시 확인은 백그라운드에서 수행하고 진행·취소를 표시한다. 공개 릴리스 조회에 사용자 Git 인증 토큰을 가져오지 않는다.

배포 asset 이름은 `Bough-{tag}-win-x64.exe` 또는 `Bough.exe`를 사용한다. 공식 저장소·태그·파일과 일치하는 다운로드만 허용하며 임의 주소 입력은 제공하지 않는다. 현재 버전은 실행 앱의 `AssemblyInformationalVersion`에서 읽고 설치 경로는 `Environment.ProcessPath`를 사용한다.

공식 asset의 SHA-256 digest로 완전한 다운로드를 확인한 파일만 자동 교체에 전달한다. digest가 없거나 일치하지 않으면 자동 교체하지 않고 이유와 릴리스 페이지를 제공한다. 취소·실패 정리는 해당 요청이 만든 파일에만 적용한다. 다른 앱 프로세스·사용자 저장소·설정·로그를 삭제하지 않는다.

## 종료 후 단일 파일 교체

업데이트는 사용자가 **업데이트 후 재시작**을 눌러 진행한다. Git 실행·대기 작업을 강제로 끊지 않으며 기존 앱 닫기와 충돌 초안 확인을 유지한다. 닫기가 취소되면 현재 앱과 실행 파일을 유지한다.

임시 보조 프로세스는 원래 앱의 정상 종료를 기다린 뒤 고정한 설치 경로의 exe를 교체하고 같은 경로에서 다시 실행한다. 단일 exe 배포를 유지하며 별도 영구 updater 배포물을 요구하지 않는다. 교체 직전에도 고정 경로·다운로드 정보를 확인하고 교체·재실행 실패 시 기존 exe를 복원하거나 유지한다. 임의 프로세스 종료·권한 상승·재부팅 예약은 추가하지 않는다.

보조 프로세스는 현재 실행 파일의 임시 사본이며 전용 시작 인수에서 사용자 설정·Avalonia·로그를 초기화하지 않는다. 정상 Main 닫힘과 UI 수명 종료 후 승인, 원래 PID·시작 시각의 실제 종료를 모두 기다린다. 준비된 후보와 기존 exe를 다시 확인하고 설치 폴더 안에서 원자적으로 교체하며 기존 파일을 백업한다. 새 버전 실행 실패 시 확인한 기존 파일을 복원해 같은 경로에서 다시 연다. 복원도 실패하면 백업을 보존하고 성공했다고 표시하지 않는다.

조회·다운로드 중 설정 화면이 분리되면 요청을 취소하고 늦은 표시를 폐기한다. 정상 종료 요청을 기다리는 동안의 View 분리는 요청 취소나 검증 파일 삭제 사유가 아니다. 정상 닫기 수락 전에는 UI Presenter가 다운로드를 소유하며, 수락 후에는 설치 담당이 준비 사본을 소유한다. 닫기를 거절하면 현재 화면에서 검증된 다운로드로 종료 요청만 다시 할 수 있다. 화면이 끝난 실패·거절 결과는 await 종료 후 해당 요청 파일만 정리한다.

현재 저장소뿐 아니라 모든 저장소의 Git 실행·대기 작업과 앱의 진행 중인 준비·설정 작업을 종료 전에 확인한다. 미저장 충돌 초안은 기존 닫기 확인으로 보호한다. 업데이트 작업 때문에 부모 Git Settings의 Git busy 상태를 켜지 않는다.

일반 개발 실행은 업데이트로 `dotnet.exe`나 IDE 출력 파일을 교체하지 않는다. 기존 사용자 설정·최근 저장소 목록·로그 저장 위치와 정상 실행 경로는 유지한다.

## 구현과 인계

앱 버전·릴리스 조회·다운로드·설치·복원·재실행은 `Bough.App/Infrastructure/Updates`의 배포 인프라 책임이다. 버전 비교 타입과 릴리스·조회·진행·검증 다운로드·설치 모델은 `Bough.App/Infrastructure/Models/Updates`에 타입별 파일로 둔다. Git·충돌을 소유하는 `Bough.Core`와 업무 Domain은 앱 제품 버전·업데이트 타입·공식 릴리스 주소·설치 정책을 참조하지 않는다.

설정의 입력·표시·요청 수명은 기존 View·ViewModel·AppUpdatePresenter, 구성·시작·정상 종료는 App·Program과 재시작 Presenter가 연결한다. 원본 코드·인수를 가진 독립 ApplicationUpdateException을 기존 표시 경계에서 지역화하며 GitException을 상속하지 않는다. 기존 AppUpdateCore 접두사 키는 호환용 식별자로 유지하며 책임 경로나 예외 상속을 뜻하지 않는다.

- 작업자 1: 설정의 업데이트 영역·바인딩 상태·Presenter·문구와 입력 연결. 큰 GitSettings ViewModel 안에 HTTP·파일 교체 로직을 넣지 않는다.
- 작업자 3: 정식 릴리스 API·버전 비교·다운로드·검증·교체의 App 배포 인프라 책임과 시작·DI·정상 종료·재실행 연결.
- 총괄: 실제 구현한 API와 종료 요청 계약을 조정하고 최종 한영 문자열을 Excel·JSON에 병합한다. 문서와 릴리스 게시를 관리한다.

작업자 3이 실제 API·모델을 먼저 인계하고 작업자 1이 해당 계약을 소비한다. 미인계 타입이나 임의의 대체 API를 호출하지 않는다. HTTP 읽기를 Git 변경 FIFO에 넣거나 새 범용 완료 계층·작업 큐를 추가하지 않는다.

현재 추가 검증 중단 방침을 유지한다. 필요한 소스 읽기·구현·문구 인계만 진행하고 빌드·테스트·UI 실행·업데이트 설치 재현·하네스·diff check·리소스 대조는 사용자가 다시 요청한 범위에서만 수행한다. 실제 반영 여부는 [구현 현황](../Docs/CurrentStatus.md)을 따른다.
